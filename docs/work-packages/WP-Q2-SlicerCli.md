## 1. Goal

Every PrusaSlicer invocation goes through one module that builds the arguments, limits how many
processes run at once, cleans up temp directories and turns CLI output into errors. A PrusaSlicer
version change then touches one file for arguments, and no client can start an unbounded number of
slicer processes.

Today `slicer/cli.ts` (`runSlicer`) is the only process start, but arguments are built in three
places (`jobs.ts`: `--export-gcode --load … --dont-arrange --loglevel 3`; `step.ts`: `--export-stl`;
`cut.ts`: `--cut …`), and `step.ts`/`cut.ts` each carry their own `SlicerRunner`, ANSI/`cleanLine`,
`failureLine`/`cutFailureLine`, temp-dir logic and (in `cut.ts`) a local `readMesh`.
`POST /api/convert/step`, `POST /api/cut` and the headless STEP import (`plater/meshes.ts` →
`convertStep`) call `runSlicer` directly, outside the job queue, so `MAX_JOBS` does not apply.

## 2. Acceptance criteria

- AC-1 All CLI argument lists are built in `server/src/slicer/commands.ts`
  (`exportGcodeArgs`, `exportStlArgs`, `cutArgs`, `helpArgs`). `grep -rn "'--" server/src --include=*.ts`
  outside `commands.ts` and tests finds no CLI flag.
- AC-2 One shared limiter: at most `MAX_CLI_PROCESSES` (env, default = `MAX_JOBS`) PrusaSlicer
  processes run at the same time across jobs, STEP conversion and cut. Further calls wait (FIFO).
  Slicing jobs keep their own queue semantics; the limiter sits below it.
- AC-3 A STEP or cut request whose client disconnects (`res.on('close')` while `!res.writableEnded`;
  `req.on('close')` fires already when the body was read) kills its process (or removes it from
  the wait queue) and removes the temp directory.
- AC-4 SIGTERM/SIGINT also stops running STEP/cut processes (today `shutdown.ts` only stops jobs).
- AC-5 `cleanLine` and `failureLine` exist once, plus a new helper `withTempDir`. The private
  `readMesh` of `plater/meshes.ts` moves to `slicer/threemf/mesh.ts` and is used by both
  `plater/meshes.ts` and `cut.ts` (which drops its local copy; `slicer/` must not import `plater/`).
- AC-6 400 answers of STEP/cut keep their wording but no longer contain absolute temp paths
  (replace the temp dir with `<tmp>`).
- AC-7 Behaviour otherwise unchanged: all HTTP statuses and bodies; G-code output for the e2e
  fixtures identical except the `; generated by PrusaSlicer … on <date>` header line.

## 3. Binding decisions

- **No engine interface.** `commands.ts` is a set of pure functions returning `string[]`; it is a
  seam for PrusaSlicer, not an abstraction over slicers.
- The limiter is a small in-module semaphore (no new dependency). Export it for tests.
- `runSlicer` keeps its signature; it acquires/releases the limiter internally and accepts an
  `AbortSignal` (already used by jobs) for AC-3.
- Output-size guard: reject a STEP result STL larger than `MAX_UPLOAD_BYTES` with 400 instead of
  reading it unbounded.

## 5. Pitfalls

- The job queue already serialises slicing jobs. Do not let a job hold a queue slot **and** wait
  for the limiter in a way that deadlocks when `MAX_CLI_PROCESSES < MAX_JOBS`; acquire the limiter
  only around the process itself.
- On Windows the slicer may be a `.cmd` wrapper; keep the existing process-tree kill.
- Progress parsing (`^\s*(\d{1,3})\s*=>`) stays where it is; only the helpers move.
